## 現在のAGENTS.mdは動作を複数の目的に対応できるようにセクションを作成して、各セクションの内容を記述している。構築中のフレームワークでは、実験計画、コード開発、分析など複数の処理目的がある。AGENTS.mdの構成を階層的にし、まず、TOPレベルのAGENTS.mdにはグローバルなルールと実験計画、コード開発、分析などの各処理の分岐を書く。作業中にユーザが「コード開発を行う」などプロンプトを与えると、実際のコード開発の記述があるcoding_AGENTS.mdをロードするという仕組みはどうだろうか。有効に働くかどうか、メリット、デメリットを調べて。



これはかなり良い発想です。
 そして同時に、慎重に設計しないと壊れやすい部分でもあります。

結論から言うと：

> ✅ 有効に働く可能性は高い
>  ⚠️ ただし「切替ロジック」を曖昧にすると破綻する

順番に整理します。

------

# 🧠 まず、あなたがやろうとしていること

今のAGENTS.mdは：

- 実験
- 分析
- notes更新
- provenance
- コード開発

を全部一枚に書いている。

問題：

- ルールが巨大化
- モードが混ざる
- LLMがどのルールを優先すべきか迷う

そこで：

## 🏗 提案構造

TOPレベル：

```
AGENTS.md
```

内容：

- グローバル原則
- モード分岐ルール
- モード検出ロジック
- 各モードへの委譲

各モード：

```
agents/
  experiment_AGENTS.md
  analysis_AGENTS.md
  coding_AGENTS.md
```

ユーザが：

> 「コード開発を行う」

と言ったら：

→ coding_AGENTS.md を読み込む

------

# 🎯 これは有効か？

答え：

> 設計が明確なら、有効。

理由を分解します。

------

# ✅ メリット

## 1️⃣ 認知負荷が下がる

今のAGENTS.mdは：

- かなり重い
- ルールが交錯している

モード分離すれば：

- 分析中は分析ルールだけ
- コード開発中は開発ルールだけ

明確になる。

------

## 2️⃣ モード衝突が減る

今起きうる問題：

- 分析中にコード修正ルールが発火
- コード開発中にanalysis provenanceが強制される

分離すれば：

- 明確に排他制御可能

------

## 3️⃣ 将来拡張しやすい

例えば：

- proposal_AGENTS.md
- paper_AGENTS.md
- grant_AGENTS.md

も追加可能。

これは研究OSとして自然。

------

# ⚠️ デメリット

## 1️⃣ モード検出の曖昧性

問題：

ユーザが

> 「これちょっと直したい」

と言った場合：

- コード修正？
- 実験設計変更？
- 分析？

LLMは誤判定する可能性がある。

------

## 2️⃣ コンテキスト分断のリスク

分析モード中に：

- ちょっとコード見たい

となった場合、

モードを切り替えると：

- 分析provenanceが中断
- event記録漏れ

が起きる可能性。

------

## 3️⃣ AGENTS読み込み保証問題

LLMは：

- 必ずしも「ファイルを読む」保証がない

明示的に：

> Load coding_AGENTS.md

と命令しないと読まない可能性がある。

------

# 🔥 本質的な設計課題

あなたのフレームワークは：

> 状態遷移型システム

になりつつある。

つまり：

```
MODE = {experiment, analysis, coding}
```

を持つ。

これを曖昧にすると壊れる。

------

# 🧠 正しい設計にするなら

TOPレベルAGENTS.mdは：

```
1. Always determine MODE first.
2. If ambiguous → ask user.
3. Explicitly state current MODE.
4. Load corresponding MODE AGENTS file.
5. Apply only those rules.
```

とする。

------

# 🎯 重要：MODEを明示的に宣言させる

例：

AIは必ず最初に言う：

```
[MODE: Analysis]
```

とか。

これを入れるだけで、

- 人間も分かる
- ログも明確
- 切替も明確

になる。

------

# 🧩 ベストプラクティス構造

```
AGENTS.md (top)
agents/
   experiment.md
   analysis.md
   coding.md
```

TOP：

- グローバル原則
- モード検出ルール
- 切替規則
- 競合解決規則

各モード：

- 具体的行動規則のみ

------

# 🧠 重要なルール（絶対入れる）

1. モードは排他的
2. モードは明示的に宣言
3. 切替時はログに残す
4. analysis中はanalysis優先
5. coding中は実験結果を書き換えない

------

# 🔬 実運用で有効か？

あなたのケースでは：

- 実験
- 分析
- コード開発

が明確に分かれる。

だから：

> 有効に働く可能性は高い。

特に analysis provenance を厳格に守るなら、
 モード分離は強力。

------

# ⚖️ 最終評価

| 項目         | 評価          |
| ------------ | ------------- |
| 構造明確性   | ◎             |
| 拡張性       | ◎             |
| 誤作動リスク | △（検出次第） |
| 運用負荷     | 中            |
| 研究OS適合度 | 非常に高い    |
