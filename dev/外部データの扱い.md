------

# 🎯 結論（先に言う）

外部データは：

> コピーしない
> 参照を保存する
> スナップショット情報だけ固定する

が原則です。

------

# 🧠 まず前提整理

外部データには3タイプあります。

## ① 静的データ（ほぼ変わらない）

例：

- 公開材料データセット v1.2
- DOI付き論文データ

→ これは **参照＋バージョン記録**で十分。

------

## ② 更新されるDB（材料DBなど）

例：

- 社内材料DB
- クラウドAPI
- 実験室の測定DB

→ これは危険。
「今と同じデータが取れる保証がない」

------

## ③ 巨大データ（コピー不能）

例：

- TB級シミュレーションデータ
- HPCストレージ

→ フルコピーは現実的でない。

------

# 🎯 軽量ルールとは何か？

軽量ルールとは：

> 外部データ対応を
> 最小限の記述追加だけで扱う方針

です。

つまり：

- 新しいサブシステムは作らない
- 新しいディレクトリも増やさない
- 既存の config.yaml / run_summary.json / logs に
  必要最低限の情報だけ追加する

というアプローチ。

------

# 🧠 何を“軽く”するのか？

重くなる方向は：

- 外部データ専用の仕様を作る
- 専用スキーマを設計する
- 専用ツールを追加する
- external_provenance.json を必須にする

軽量ルールは：

> 「最低限これだけ書いていればOK」

という実用主義。

------

これだけ。

# 外部データ取扱仕様（軽量ルール v0.1）

## 目的

外部DB・外部ストレージ・外部API等を参照する実験でも、後から

- 何を参照したか
- どの条件で参照したか
- 実際に何を使って計算したか（最低限）

が分かる状態を作る。
**データ本体の完全保存は要求しない。**

------

## 適用範囲

- 材料DB（社内DB、公開DB、API）
- 外部ストレージ（HPC領域、S3等）
- 外部データセット（DOI/URLで参照可能なもの）

※機密・巨大データを含む可能性がある前提。

------

## 設計原則

1. **コピーしない**（原則）
2. **参照を保存する**（必須）
3. **“実際に使用した値”を結果側に残す**（推奨）
4. **analysis は特別扱いしない**（run_summary と config を読むだけで成立）
5. **構造を増やしすぎない**（新規ディレクトリ必須化なし）

------

## 仕様

### 1) config.yaml に external_data を追加できる（任意だが推奨）

`experiments/<exp>/config.yaml` に以下のブロックを**追加可能**とする。

```yaml
external_data:
  - name: materials_db
    type: database        # database | api | dataset | filesystem
    locator: "material_id=1234"     # query / path / DOI / URL など自由記述
    version: "v2.1"       # DB版、API版、dataset版など（分かる範囲で）
    retrieved_at: "2026-03-03T10:12:00+09:00"   # 分かれば
    note: "Elastic modulus used for SSOR omega sweep"  # 任意
```

#### ルール

- `external_data` は **配列**（複数ソース対応）。
- `locator` は **人が読める最小参照**（クエリ、ID、URL、パス、DOIなど）。
- `version` が不明なら省略可。
- ここは **参照情報のみ**。生データの貼り付けは禁止（巨大化防止）。

------

### 2) run_summary.json に external_data_used を記録できる（推奨）

`results/<exp>/run_summary.json` に、計算で実際に使用した外部データ由来の値を **要約として**残す。

```json
{
  "iterations": 162,
  "runtime_sec": 2.55,
  "converged": false,
  "external_data_used": [
    {
      "name": "materials_db",
      "locator": "material_id=1234",
      "values_used": {
        "elastic_modulus_GPa": 210.5,
        "poisson_ratio": 0.30
      }
    }
  ]
}
```

#### ルール

- “参照した”ではなく、**使用した値**を残すのがポイント。
- 生データ全量は不要。**モデルに入った値だけ**でよい。
- 値が多い場合は「統計量（min/max/mean）」だけでもよい。

------

### 3) logs/.json で provenance を補強（任意）

外部参照がある場合、`logs/<exp>.json` にも短く残すと強い。

- 参照した外部ソース名
- 参照時刻（可能なら）
- 実行ホスト名や環境など既存のprovenance

※ただし **二重管理**を避けるため、詳細は config / run_summary に寄せる。

------

## 運用ルール

### A) 外部データがある実験の最低条件（推奨）

- config.yaml に external_data を書く（参照）
- run_summary.json に external_data_used を書く（使用値）

これで AI は十分に比較・要約・仮説生成ができる。

------

### B) analysis での扱い

analysis は “外部データ特別扱い”しない。

AIは：

- config.yaml の external_data（参照条件）
- run_summary.json の external_data_used（使用値）

を見て、目的（objective）との整合や比較を行う。

------

### C) 注意事項（軽量ルールの限界）

以下の場合は軽量ルールだけだと再現が難しい：

- DBが上書き更新される（同じIDでも値が変わる）
- APIが非決定的（返す値が変動）
- 生データそのものが結論に直結する

この場合は v0.1では「例外扱い」とし、必要なら追加で：

- レスポンス抜粋の保存
- ハッシュ（checksum）記録
  を検討する（v0.2課題）。

------

## AI向けチェック項目（AGENTS.md に入れる用）

外部データがある実験をレビューする際、AIは必ず：

1. external_data（参照）が config にあるか
2. external_data_used（使用値）が run_summary にあるか
3. locator と values_used が矛盾していないか
4. baseline実験と外部データ条件が揃っているか

を確認し、矛盾があれば「要修正」とする。
